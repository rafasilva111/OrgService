# Authorization

Centralized, **database-level** authorization: visibility is expressed as query filters, never
filtered in Python. Two entry points cover the whole platform.

## Concepts

- **Permissions** are atomic action codes `module.verb` (e.g. `request.view`, `request.close`).
  Read (`view`) and write (`create/update/close/…`) are **separate atoms** — having visibility never
  implicitly grants mutability.
- **Roles** are reusable groups of permissions, not tied to any organization.
- **Scope** is decided by *where* a person is a member (`OrganizationMembership`) and optionally
  restricted further by `ServiceAccess`.

## The two entry points (`apps/common/authorization.py`)

```python
# 1) Single object: can this user perform this action on this resource?
from apps.common.authorization import can

can(user, "request.view", request)  # -> bool

# 2) Collection: give me this user's visible rows (a QuerySet).
Request.objects.visible_to(user)  # -> <AuthQuerySet> (default action = request.view)
visible(Request.objects.all(), user)  # alias
```

Every model gets `.visible_to()` for free because `TimeStampedModel.objects` is a manager built
from `AuthQuerySet`. Models declare how to reach the scope root:

```python
_AUTH_ORG_FIELD = "service__organization"  # path from the model to an Organization
_AUTH_SERVICE_FIELD = "service"  # optional path to a Service
```

## How `authorization_scope_q(model, user, action)` works

1. Anonymous / unauthenticated → no rows.
2. Superuser → all rows.
3. Find the user's active persons and their memberships.
4. For each membership whose **role grants the action** (code in the role's active `RolePermission`s):
   - **No `ServiceAccess` rows** → grant covers every service in the membership organization's
     **subtree** (including offspring organizations, **not** ancestors, **not** siblings):
     `Q(org_field__in=descendant_org_pks(membership.organization))`.
   - **Has `ServiceAccess` rows** → grant covers exactly those services:
     `Q(service_field__in=service_ids_of_access)`.
5. Build a single `Q` — union of all grants (`OR`); merge across multiple memberships/roles.

The descendant organizations subquery is a real SQL subquery using the `ltree` descendants lookup
(`path <@ '…'`), so entire subtrees resolve in one query.

## Semantics (locked by tests)

| Scenario | Result |
|---|---|
| Membership at Municipality, role grants `request.view` | sees requests in **both** Parish services |
| Sibling parish under the same District (not a descendant) | **not** visible — no uphill/sideways flow |
| Grandparent organization | not included (access only flows down) |
| Membership + `ServiceAccess(membership, service_a)` | only service_a's rows visible; others hidden |
| Role without the action's permission | nothing visible for that action |
| Superuser | everything |
| Anonymous / logged-out | nothing |

## Example SQL (generated by the scope)

```sql
SELECT ... FROM requests_request
WHERE service_id IN (
    SELECT U0."id" FROM services_service
    WHERE U0."organization_id" IN (
        SELECT U0."id" FROM organizations_organization
        WHERE U0."id" = 2 OR U0."path" <@ 'dist.muni'
    )
) OR service_id IN (…)   -- additional memberships / service restrictions
```

## Service access semantics

`ServiceAccess(membership, service)` rows, when present, **restrict** a membership to exactly those
services (under any organization reachable through the same memberships/roles). An empty set of rows
means “everything under the organization subtree”.

## How to add a new model

1. Inherit from `apps.common.models.TimeStampedModel` (brings the manager).
2. Declare `_AUTH_ORG_FIELD` (required) and `_AUTH_SERVICE_FIELD` (optional).
3. Seed its read/write permissions in `apps/access/management/commands/seed_rbac.py` and grant them on
   the relevant roles.
4. `Request.objects.visible_to(user)` and `can(user, "<app>.view", obj)` now work with no other code.
